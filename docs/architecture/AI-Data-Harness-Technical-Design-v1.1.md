## 1. 本次决策

AI-Data Harness 以企业云端数字人为统一产品入口。用户通过 CLI 发起、查询和推进研发事项；云端数字人平台承载从需求到交付的持久化管理，并调度已有 Agent 执行能力。AI-Data 团队提供数据研发领域知识、工作方法、工具适配、流程模板与验收规则，现有数据平台继续执行计算、发布和调度。

这里的“完整能力集成在数字人中”是产品与服务边界：用户面对同一个数字人，背后由云端 Agent、事项服务、工作流、产物存储和执行控制共同完成交付。流程等待、权限判断、证据有效性和外部操作恢复由程序落实。

当前方向不要求 AI-Data 另建一套通用 Agent 引擎或独立工作台。后续增加工作台时，它通过同一云端事项契约读取状态和发送命令；一个事项的阶段推进始终只有一个权威来源。

## 2. 已确认事实、目标与未知项

| 分类 | 本轮信息 | 对设计的影响 |
|---|---|---|
| 用户确认的现状 | 通过 CLI 访问部署在云端的数字人 | CLI 为首期主入口；实际命令与返回格式待获取 |
| 用户确认的现状 | 数字人可以自主查表、读代码、调用工具、测试和修改 | 已有 Agent 任务执行闭环，优先复用 |
| 用户确认的现状 | 可以优化知识库等外挂信息 | 数据专业能力可持续改进；具体装载、版本及扩展机制待核验 |
| 用户描述的现状 | 云端支持 Claude Code、Codex 和 DeepSeek Harness 等引擎 | 按实际可用引擎接入；不推断插件格式、会话和恢复机制通用 |
| 用户确认的目标 | 希望完整需求到交付过程也由云端数字人管理 | 将通用事项管理、工作流和运行治理纳入云端平台能力要求 |
| 待核验 | 事项持久化、事件续跑、隔离、身份权限、产物管理、幂等和审批 | 自主执行能力不能作为这些能力已具备的证据 |
| 沿用的设计输入 | 现有 MCP、自动发布、数据调度，以及复杂数仓资产与语义需求 | 来源为 v1.0 记录的既有讨论；本轮未重新审计实际平台接口 |

云端团队应提交能力盘点：已支持、部分支持、未支持、待核验，并附实际版本、接口或演示证据。当前不预填任何完整平台能力为“已支持”。

## 3. 概念与归属

| 概念 | 本方案中的含义 | 典型内容 |
|---|---|---|
| 数字人 | 用户可调用的专业执行者及其云端服务能力 | 数据研发数字人，关联能力配置和授权范围 |
| Agent 执行机制 | 一次任务中获取上下文、调用工具、执行与修复的循环 | 查表、写 SQL、测试、根据结果修改 |
| Harness | 承载 Agent 工作的运行与控制机制；本项目还将研发事项级管理纳入产品范围 | 环境、上下文、执行约束、持久流程、产物与验收 |
| 知识 | 有来源和版本的业务定义、背景与经验 | 指标口径、数据分层标准、历史案例 |
| Skill | 可复用的工作方法，可包含脚本和模板 | 资产定位、SQL 研发、影响分析方法 |
| 工具／MCP | 访问实时事实、执行受控操作的接口 | 当前代码、表结构、血缘、SQL 测试、发布状态 |
| Plugin／能力包 | 专业能力的版本化装配与交付单位 | Skill、工具映射、流程、验证器及其依赖 |
| 研发工作流 | 管理阶段、等待、失败分支和完成条件的程序 | 需求确认、开发、验收、授权、发布和关闭 |

这些名称用于约定职责，不预设云端必须使用某个厂商的实现格式。若云端支持原生 Skill 或插件，按其规范装载；否则以任务说明、脚本和配置表达相应能力，并保留可追溯版本。后续按实际复用和安装需求决定插件封装形式。

## 4. 目标架构与团队分工

### 4.1 产品入口与服务边界

| 层次 | 职责 | 权威信息或结果 |
|---|---|---|
| CLI 及未来其他入口 | 认证、提交命令、展示状态、获取产物 | 客户端缓存仅用于展示，不决定阶段或授权 |
| 云端事项与工作流服务 | 管理需求修订、阶段推进、人工事件、等待与恢复 | 事项修订、流程历史及命令处理结果 |
| 云端 Agent 执行环境 | 装配上下文、工作空间和工具，调用数字人执行阶段任务 | 执行记录、候选代码及阶段产物 |
| 云端执行控制与验收 | 校验计划、产物、权限，执行验证器，管理外部操作 | 验收证据、授权、操作记录和核实结果 |
| AI-Data 专业能力 | 领域知识、流程模板、Skills、SQL 与语义验证规则 | 经维护和评审的能力版本、基准案例 |
| 现有数据平台 | 元数据、代码源、计算、发布、调度与数据恢复 | 实际代码版本、运行状态和数据结果 |

云端可以复用企业已有工作流、数据库、制品库和权限服务，不要求全部作为新服务开发。研发事项流程与数据计算 DAG 各自保留职责，避免双方同时负责触发同一批下游任务。

### 4.2 责任分配

| 交付范围 | 主责团队 | 协作与验收 |
|---|---|---|
| 事项对象、CLI 契约、后台工作流、恢复和事件 | 云端数字人平台 | AI-Data 验证研发过程能完整表达 |
| 隔离环境、身份、产物存储、预算、审计、扩展加载 | 云端数字人平台 | 企业 IAM、SRE 和验证人员参与 |
| 数据研发流程、口径、Skill、验收程序与评测集 | AI-Data | 业务 Owner 和数据治理确认语义 |
| MCP／API 能力语义、发布／重跑／结果查询／恢复接口 | 数据平台 | AI-Data 做领域映射；云端实施执行控制 |
| 超时核实、并发冲突、取消及补偿的端到端语义 | 云端与数据平台共同承担 | AI-Data、SRE 通过故障场景验收 |
| 生产授权政策与自动化范围 | 企业授权责任人 | 云端落实约束；AI-Data 提供业务条件 |

一个团队可以兼任多个角色，但每项交付都要有明确负责人。现有接口缺少可靠查询或去重时，应记录可自动化边界和补齐责任，不能由模型猜测弥补。

## 5. 事项、会话与执行身份

| 对象 | 建议标识 | 生命周期和用途 |
|---|---|---|
| 数字人定义 | `digital_human_id`、`definition_version` | 描述能力与运行配置，可供多个事项使用 |
| 研发事项 | `changeset_id` | 从需求建立到交付归档的稳定身份 |
| 事项修订 | `changeset_id`、`revision` | 一版需求、计划输入及依赖；变更保留历史 |
| 工作流执行 | `workflow_run_id` | 某次持久流程执行，与引擎实际运行 ID 映射 |
| 阶段执行 | `stage_run_id`、`attempt` | 一次开发、验证或其他阶段尝试；记录输入和结果 |
| Agent 会话 | `session_id` | 可结束、压缩或重建，关联所属阶段 |
| 外部操作 | `operation_id`、`external_id` | 一次逻辑发布或重跑及目标平台的实际记录 |

这些是逻辑字段建议，允许映射云端既有名称。一个事项可以经历多个会话和阶段尝试；重启进程不应创建重复事项或重复生产动作。工作流迁移、重新执行和引擎更换必须保留前后运行关联。

业务知识、聊天上下文、事项状态分别管理。状态查询返回服务端记录和更新时间；模型根据这些记录解释进度。不能从对话总结重建已发布事实或授权结论。

## 6. 完整研发流程如何在数字人中运行

1. 用户经 CLI 提交需求。平台校验身份和请求去重标识，持久化事项，返回稳定 ID；断开终端不取消事项。
2. 数字人整理需求契约，识别口径与验收缺口。需要补充时，平台保存待回答项并等待用户事件。
3. 平台装配指定版本的能力、知识引用、代码基线和工具权限，数字人完成资产检索、影响分析和计划草案。
4. 平台运行计划校验：目标范围、依赖关系、权限、资源和必要证据满足要求后，启动开发阶段。
5. 数字人在隔离环境开发、测试和限次修复，提交代码、配置、说明与未解决问题。
6. 平台运行独立验证器，将结果绑定本次需求、代码、配置、数据和环境版本。失败返回修复或重规划，预算耗尽则保留产物并报告原因。
7. 按企业政策取得指定计划与产物的授权。等待期间保存状态并释放可释放的执行资源；收到有效事件后继续。
8. 平台通过受控执行路径复用现有发布和调度，登记外部操作，查询实际版本、节点和分区结果；未知结果先核实。
9. 完成生产数据验收，归档代码、证据、授权和运行记录。产生的知识候选按审核流程回写，状态明确可查。

阶段成功仅说明该阶段满足契约；事项关闭需要完整交付证据。沿用 v1.0 第 6、13、14、15 章的阶段条件、独立验收、恢复及授权约束。

“恢复”指根据已持久化事实继续推进。尚未提交的模型输出或工作区改动可能需要重新生成；结果不明的外部操作需要核实。实现应说明检查点粒度，不承诺每个模型 token 或任意工具调用都可以无损续接。持久事件历史和外部操作幂等是不同机制，参见文末资料。

## 7. AI-Data 向云端交付什么

### 7.1 一套可版本化的专业配置

| 内容 | 最小交付 | 平台所需扩展点 |
|---|---|---|
| 数字人专业定义 | 适用域、任务类型、负责人、能力版本 | 数字人配置、启用范围与依赖检查 |
| 需求和阶段契约 | 必填口径、阶段输入输出、产物类型 | Schema 校验和结构化结果接收 |
| 流程模板 | 阶段依赖、分支、等待、完成与失败条件 | 持久工作流模板或可注册阶段实现 |
| 知识与上下文策略 | 经确认定义、来源、检索范围、版本引用 | 按权限检索、来源引用和依赖记录 |
| Skills 与脚本 | 工作步骤、SQL 模板、资产分析方法 | 受控装载和运行，不假定原生格式兼容 |
| 工具映射 | 逻辑能力到现有 MCP／API、范围和结果语义 | 身份传递、参数校验和外部操作接口 |
| 独立验证器 | 输入契约、可执行检查、结论和证据输出 | 可由工作流直接执行的验证程序 |
| 回归案例 | 固定输入、预期产物、评分规则、失败案例 | 配置升级前评测和结果比较 |

上述可以先按云端已有配置机制交付；原 v1.0 自定义 Plugin manifest 是参考，不作为接入的强制格式。云端仅支持上传文档时，应将执行验证器、流程扩展和工具权限作为能力缺口登记。

### 7.2 验证器和控制条件的边界

AI-Data 定义如何检查客户粒度、90 天窗口、去重、空值与旧指标回归。云端负责按固定版本执行这些检查，保存输入绑定和结果，并据此判断能否进入下一阶段。

Agent 可以提出修改计划或补充测试，但改变验收口径需要形成明确修订；开发过程不能自行放宽验收条件来取得通过。最终是否执行生产操作由程序结合有效证据与授权判定。

### 7.3 知识优化与运行版本

知识优化主要解决口径和背景缺失，Skill 优化解决方法与步骤问题，工具适配解决事实获取和操作问题，验收程序解决正确性判定问题。每次改进都应在同一批版本化案例上比较结果。

任务记录数字人配置、知识引用、Skill、工具 Schema、验证器和可识别的引擎／模型配置版本。已运行事项保留原依赖；需要升级时显式迁移、重新验证并记录原因。版本锁定不冻结权限：授权撤销、能力禁用和企业强制策略在后续动作前重新检查。外部实时事实在关键动作前重查；获准知识版本并不代表目标平台的当前代码和运行状态不会变化。

## 8. 云端平台接入边界

CLI 需要覆盖提交、查询、跟踪事件、补充与修订、确认与驳回、查看产物、暂停、继续和取消。接受命令、启动执行、完成操作应分别可识别；返回结构化状态、稳定 ID、错误类型和必要的产物引用。

具体命令、传输协议和错误码由双方依据真实 CLI 共同确定。v1.0 第 17 章的 HTTP 路径用于表达逻辑契约，不要求另建平行 HTTP 服务。未来其他客户端使用同一服务端权威状态。

外部事件和人工操作需要验证来源、范围及对应修订，并处理重复和过期事件。批准后修改代码、计划或相关输入，会使受影响证据与授权失效。取消请求被接受不等于目标数据平台已经停止；云端必须继续显示和处置在途操作。

详细能力编号、CLI 语义、盘点表与故障验收见[平台能力文档](Cloud-Digital-Human-Platform-Requirements-v1.0.md)。

## 9. 最小试点与递进交付

### 9.1 试点范围

先选择一个数字人配置、一个业务域、一种主要 SQL 方言和一类真实研发需求，使用相关资产集合及可复现输入。保留对跨域消费者的只读影响查询。参考需求为“客户画像新增近 90 天逾期次数，保留现有 30 天口径”，实际口径由业务 Owner 确认。

首次沙箱验收终点是可评审代码和测试证据；完整生产交付是后续阶段的目标。CLI、任务配置和云端产物查询可以支撑首期体验。独立工作台、多个数字人协作、完整插件市场及跨引擎无缝会话迁移按实测需要增加。

### 9.2 阶段退出条件

| 阶段 | 核心工作 | 退出证据与负责人 |
|---|---|---|
| D0 接入与能力盘点 | 获取真实 CLI 契约、事项／会话模型、身份、环境、工具与产物能力；演示一次现有任务 | 云端给出可复现调用记录与能力缺口表；三方确认归属 |
| D1 可恢复沙箱闭环 | 装配首个专业配置，运行需求、分析、开发和独立验证，保存状态与产物 | 云端与 AI-Data 演示 CLI 断连、进程重启、待补充后继续；交付代码和有效报告 |
| D2 受控生产闭环 | 接入授权、发布、调度、结果核实、生产验收和恢复 | 云端与数据平台通过跨天流程、未知结果、版本失效、并发、取消和恢复验收 |
| D3 按域扩展与优化 | 增加场景、配置版本管理、回归评测与资源运营 | AI-Data 按约定质量、返工、交付周期与成本指标验收新范围 |

配套能力文档中的 P0、P1、P2 表示能力优先级，分别支撑 D1 沙箱、D2 生产和 D3 扩展；D0 负责盘点这些能力。

阶段时长和人员投入在 D0 缺口盘点后估算。v1.0 的周数及人员示意不沿用为当前承诺；专业能力开发与云端缺口补齐可以并行，但生产准入必须满足 D2 的前置条件。

### 9.3 云端能力尚未齐备时

先利用现有数字人执行能力完成沙箱试点，将缺口作为云端待交付项。测试脚本可以用于验证接口和产物，不承担隐式生产编排。若确需临时服务承载事项管理，必须明确唯一状态归属、迁移方案和退出条件，并单独评审这一架构变化。

## 10. 最小端到端验收

正常场景：提交真实需求，关闭 CLI；云端开发和验证后进入等待确认；跨天并重启执行进程后重新连接，查询同一事项；对指定版本确认，发布、等待调度并验收，最终导出交付记录。

关键故障场景：

- 已发布但响应丢失：保留逻辑操作身份，核实目标结果；可识别既有操作时复用，否则保留待核实状态并阻止盲目重复提交。
- 代码或需求在审核后变化：生成修订或新产物，受影响的旧证据和授权失效。
- 并发修改同一节点：识别版本和写入冲突，过期执行者无法继续造成受禁止的写入。
- 取消时外部任务仍在运行：说明实际状态、可取消范围及恢复处理，最终结果可追溯。
- 数字人报告完成但缺少必需证据：事项保持未完成，列出缺失验收项。

通过条件、故障步骤和证据类型在配套能力文档中细化。成功运行一次只证明该路径可用，不能替代故障与跨天验收。

## 12. 新增架构决策

| ADR | 决策 | 影响和重新评估条件 |
|---|---|---|
| ADR-009 | 通过 CLI 统一访问云端数字人，云端承载事项生命周期 | 若关键能力无法提供，明确限制或评审临时承载方案 |
| ADR-010 | AI-Data 以领域配置、工具适配和验证器扩展云端 | 云端扩展接口不足时优先形成平台需求，避免仅依赖提示词落实约束 |
| ADR-011 | 事项、修订、工作流、阶段、会话与外部操作分离 | 增加身份映射，支持跨天恢复、重试和不同引擎调用 |
| ADR-012 | 插件封装遵循实际宿主，独立工作台按需增加 | 先验证业务交付；版本追溯和权限要求从试点起保留 |

ADR-001 至 ADR-008 的事项、单一主流程、执行网关、知识权威来源、复用数据平台和分级自动化原则继续适用。

## 14. 依据与资料

- **本轮用户确认：** CLI 访问云端数字人、自主工具执行、知识外挂优化，以及完整研发事项管理集成到数字人的目标。现状能力仅按用户明确描述记录。
