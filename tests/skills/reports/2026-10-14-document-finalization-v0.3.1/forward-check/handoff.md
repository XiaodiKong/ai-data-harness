## 正文：库存差异日报设计方案 v1.1

**目标与交付范围**

为仓库主管每天汇总前一天的库存差异，支持次日 09:00 前查询。本方案采用每日批处理。

本次交付为设计文档，包含业务要求、处理流程、约束、实施计划及上线标准。部署和实际测试由后续实施阶段完成。

**数据与查询**

每日结果包含以下字段：

| 字段 | 含义 |
| --- | --- |
| 仓库编号 | 库存差异所属仓库 |
| 商品编号 | 发生库存差异的商品 |
| 差异数量 | 对应商品在该仓库的库存差异数量 |
| 日期 | 库存差异所属业务日期 |

结果按“仓库编号＋商品编号＋日期”唯一标识。数据团队在配置阶段落实来源字段映射、业务日期边界和差异数量口径，以准确汇总前一天数据。

查询权限仅授予仓库主管。值班员接收失败通知，不因接收通知而获得库存差异查询权限。

**处理与异常流程**

每天批量读取前一天的库存差异数据，完成字段整理、汇总和去重后，写入可查询结果，确保次日 09:00 前可查。

失败时通知值班员，并按“仓库编号＋商品编号＋日期”去重重试。实现上建议采用唯一键约束和幂等写入，使重复执行更新同一结果，避免新增重复记录。该实现方式需在联调阶段验证。

具体批处理开始时刻和通知渠道由数据团队在实施阶段确定。开始时刻需为处理及失败重试预留时间，满足 09:00 前可查的要求；通知渠道需能够触达值班员。

运行日志留存 14 天，用于追踪执行、失败及重试情况，并配置相应清理策略。

**预算与适用限制**

月预算不得超过 400 元。数据团队需根据实际数据量、执行时长、存储、日志及通知等计费项目进行成本测算，并据此选择和配置资源。

资源上限仅用于控制资源使用，不能作为成本已测算或月预算已满足的证据。目前没有成本收益数据，因此本方案不作收益、回本周期或经济性优劣判断，也不声称实际运行成本已验证。

当前方案适用于每日汇总、次日上午查询的需求。时效、去重、通知和权限效果均需通过实施阶段验证后才能确认。

**实施计划**

| 阶段 | 责任方 | 工作与产出 |
| --- | --- | --- |
| 配置 | 数据团队 | 落实数据来源与字段映射、业务日期边界和差异口径；确定批处理开始时刻、通知渠道和重试配置；配置唯一键、主管查询权限、14 天日志留存；完成成本测算和资源配置。 |
| 联调 | 数据团队 | 验证完整批处理流程；测试重复执行及失败重试；核实值班员通知到达、权限控制和处理时效；记录问题并修正配置。 |
| 上线 | 数据团队 | 汇总联调证据，核对上线标准与预算约束；完成部署、调度启用及运行观察，向仓库主管交付查询入口，并落实异常处理安排。 |

上述阶段属于后续实施计划，不代表本次已执行配置、联调、部署或测试。

**上线标准**

| 标准 | 判定方式 |
| --- | --- |
| 时效满足 | 前一天库存差异在次日 09:00 前可查。 |
| 无重复 | 同一“仓库编号＋商品编号＋日期”只有一条结果，重复执行和失败重试不产生重复记录。 |
| 通知到达 | 失败触发通知，值班员实际收到通知。 |
| 权限检查通过 | 仓库主管可查询，非仓库主管不能读取库存差异结果。 |

数据团队应留存上述验证证据。未完成验证前，不将设计要求视为实际运行已经达标。

维护一份可独立使用的当前正文，同时保留可审阅的决策依据、重要变更和未决事项。AI 判断是否具备验收条件，用户决定是否通过。正文准确、完整与可执行优先于形式整齐。

每轮按实际任务执行：识别有效要求与本次意图 → 整合正文及关联内容 → 检查覆盖、论证和证据 → 更新必要记录 → 在状态有变化时说明下一步。简单编辑直接完成，不强制建立表格、多个文件或审批流程。

开始时从已有材料明确用途、读者、交付范围和验收标准；信息足够就直接工作。重要缺口尽早询问，并推进不依赖答案的部分。用户委托 AI 选择时，在授权范围内提出并采用有依据的建议，注明其来源，不要求用户逐条确认常规写作选择。

支持持续维护、收敛定稿、验收后修订。遵循用户格式、长度、位置及已有结构。关键限制无法容纳于指定长度时，保留摘要并提供完整附件，或明确内容取舍待确认；不能默默删掉有效要求来满足篇幅。

## 通用使用与材料边界

本文件正文是完整的通用规则，可直接提供给其他 AI，不依赖特定工具、路径、持久记忆或平台展示配置。需要具体示例时读 [方法与示例](references/methods-and-examples.md)，需要交接格式时读 [交接模板](references/handoff-template.md)；两者均可选。

只有实际读到的材料才可作为来源。没有历史或附件时说明缺失，不重造内容；没有检索或执行能力时明确未核实、未实测。聊天环境分区输出，文件环境维护实际文件，不声称完成未执行的保存或检查。用户已有明确授权时按其范围工作，本技能不另设工具许可。

## 判断什么可以进入当前版本

区分事实、用户要求、AI 建议、假设和已确认决策。正文可以包含候选方案，但应清楚表达其条件或待决之处，不能冒充已获确认。

- 用户明确替代旧要求时更新；试探性提问、例子和备选意见不自动替代已确认决策。
- 用户提供的数据注明来源；“用户确认”不等于经过外部核实。新证据与已确认结论冲突时，指出冲突和影响，重开相应事项，不为保留旧结论掩盖错误。
- 不同来源冲突但没有明确替代关系时，说明分歧，必要时请求判断；不能仅凭材料出现得晚就认定它更权威。
- 标记“待确认”“不在范围”“接受的限制”时给出依据。AI 不得自行把阻塞项降级以进入验收，也不为无关扩展功能制造阻塞。
- AI 新发现的完善项先作为建议，不直接写成用户已同意的验收条件。若缺口确实使已有标准无法解释或满足，说明它与哪条标准的关系，再请求必要输入；不能以“更完整”为由不断抬高门槛。
- 已明确排除的事项不列为本次阻塞；后续实施所需输入另记行动。未讨论的事项不自动等于已同意排除。新证据表明排除项会影响现有标准时，说明依赖并请求调整范围，不同时声称它“不在范围”又要求确认后才能交付。

## 结构与论证：按用途选择方法

探索允许发散、比较和回退；交付按读者理解与行动顺序组织。结论先行是表达顺序，证据不足时可先说明“尚不能确定”及决定性缺口，不先认定答案再寻找支持。

| 需要解决的问题 | 执行规则 |
| --- | --- |
| 方案重点不清 | 借鉴金字塔原理：先回答核心问题，再给支持理由与必要细节；上层概括由下层支持，同层采用一致分类与顺序 |
| 背景与目的不清 | 借鉴 SCQA：简述背景、真实矛盾、需回答的问题和当前回答；不虚构冲突，也不重复已清楚的背景 |
| 范围复杂、易遗漏 | 用问题树拆分，借鉴 MECE 检查重复和关键缺口，说明覆盖范围；不强称现实问题完全互斥穷尽 |
| 判断或选型依据不足 | 借鉴图尔敏论证：关键主张需有证据、连接理由、适用条件及重要反例；方案用共同标准比较，不虚构评分或权重的客观性 |
| 问题或方案仍在探索 | 借鉴双钻，先界定问题，再比较和筛选方案；新证据可触发回退，不为定稿强行选出唯一答案 |
| 决策易遗失、完整性难判断 | 借鉴决策记录和需求追踪：记录选择与后果，把必需要求对应到正文及完成依据 |

方法无需成为标题。操作手册保留步骤顺序，参考文档按主题组织，选型文档保留必要比较。只有重大判断需要详细论证，普通内容不必填满方法表。

## 三类内容分开维护

### 1. 核心正文：当前可用的完整内容

正文保留目标、方案、理解与执行所需的理由、约束、风险、例外和适用边界，读者无需回看对话即可使用。

新结论直接融入对应章节，清除失效内容与重复补丁；同步检查摘要、表格、图示、数值、流程、示例、计划和验收标准。修改前后核对仍有效的字段、数量、责任、权限、异常处理等细节，不能因改写或概括而丢失。只修改局部时，同步其必要关联，不扩大重写范围。

避免“按你刚才的要求”“最初考虑”“这次改为”等修订叙事。历史移到记录，当前必要的设计理由仍留正文；影响方案成立的假设和风险也必须在相关位置可见。当前合法的备选路径和比较不属于应删除的历史。

正文内的验收条目也应直接陈述当前要求，例如“次日 08:00 前可查”，不写“已经把一分钟要求改为次日可查”。需要审计修改是否完成的检查项放在交付说明或变更记录中。

维护完整正文不等于每轮在聊天重发全文：文件已更新时可给链接和简短说明；探索时可只展示受影响部分并标明范围。提交验收或交接时必须提供完整版本或接收者可访问的完整文件，“其余同上”或省略章节不算完整交付。超过输出限制时分批交付，全部到齐前不称已完成交付。

### 2. 论证、决策与变更记录：为何这样决定

提供可审阅的分析成果和简明理由，不输出逐步内部推理或复述整段聊天。

重要决策记录问题与背景、选择、依据、重要备选、后果与适用边界、确认来源；需要时增加重审条件。实质变更另记对应版本、变更内容、影响范围，避免与决策解释混成流水账。微小编辑不制造日志。

保留真实历史；错误记录用更正说明处理。未知来源、日期或确认状态如实标明，不编造。正文与记录互相对应，但不重复复制全部内容。

### 3. 协作状态与未决事项：现在缺什么

未决事项说明问题、影响、是否阻塞本次交付和所需输入。已有答案就融入正文并关闭；用户接受限制或移出范围时记录其明确决定，不把它写成技术问题已解决。

三类内容可以使用独立文件或清楚分隔的附录；不要求三个固定文件。状态、验收说明和记录默认放正文之外，用户模板另有要求时遵循模板。

同页交付时，可用“正文：<文档名及版本>”承载当前方案，在其后以同级标题“附录：决策与变更记录”“交付说明”分隔。不要把历史记录或验收请求继续编号成正文的下一章，也不要将含这些内容的整份回复称为“完整正文”。只取出正文区应能独立使用，并且不带聊天回顾或向用户发出的验收请求；具体标题可沿用用户格式。

## 交付检查

对约定范围检查实际内容，不因章节齐全、篇幅长或措辞流畅就宣告完成：

1. **覆盖与保留**：必需内容有实质回答，无占位或静默遗漏；本轮未改变的有效要求仍在。
2. **一致性与边界**：全文、图表及记录中的当前结论一致，关键变更的关联影响已经处理；正文与过程记录、协作状态的边界清楚，排除项未回流为本次阻塞。
3. **论证与证据**：关键结论有足够依据，假设、反例及适用限制明确；拟议的验证不写成已完成的验证。
4. **独立可用**：读者能理解当前方案并采取约定行动；完整文件已实际提供或更新。
5. **交付条件**：必要问题已解决，没有未经用户认可而降级的阻塞项。

复杂交付可用“要求—正文位置—完成依据—缺口”表，短文档用简短检查说明。不要用总体评分抵消关键失败。自行能修复的直接修复，无法解决的具体指出；检查未完成时不声称“全文检查通过”。

分别判断文档完整性、结论的证据充分性及方案是否实际验证。实际测试若不属于本次文档交付，不凭空要求先部署；但依赖未经验证的关键假设才能成立的推荐，必须限定结论，或保持待决，不能只在附录写“未验证”就宣告成立。

## 版本与主动验收

工作阶段可为“问题界定、方案探索、方案整合”，允许回退；验收状态另行管理。日常不重复显示全部字段，只说明有意义的状态变化、缺口或下一步。

| 验收状态 | 条件 | 行动 |
| --- | --- | --- |
| 对焦中 | 必要内容、关键选择或交付检查未完成 | 明确缺口，推进可完成部分 |
| 待验收 | 约定交付条件满足，完整版本已经提供 | 主动请求用户对该版本及范围确认 |
| 已验收 | 用户明确确认具体版本和范围通过 | 记录依据，保留基准 |

沿用版本规则；没有时使用简单编号。实质内容变化产生新版本，同一编号不能指向不同实质内容。区分技能版本、文档版本与验收记录。保留明确引用的原验收基准；文件有可恢复版本历史就沿用，否则在覆盖已验收内容前保存快照。聊天场景引用原完整版本，不虚称已创建文件。

首次具备验收条件或实质修改后的版本再次具备条件时，主动交付并简述：**版本与范围、完成依据、已知限制和剩余事项**，再请用户选择“验收通过、修改后再验收、继续对焦”。不用固定口令，不重复催验收；用户明确继续探索时不施加定稿压力。

“这版通过”“就按这个定稿”等指向明确时可认定通过；沉默、一般赞许、局部认可或其他 AI 的完成声明都不等于全文验收。仅局部通过时记录范围，全文仍按实际条件判断。指向不清时只澄清必要部分。

已确认要求、局部认可和全文验收分别记录。“同步策略没问题”只确认该范围，不扩展到权限或异常处理，也不撤销其他已确认要求。全文尚未验收但已满足条件时，只请求整版确认；不将已确认要求重新列成待决清单，不要求逐条重复批准。

验收后实质修改的当前版本重新判断为对焦中或待验收，原版本的通过记录仍保留；列明受影响范围，不让未受影响部分无故重做。拼写、排版修正可说明不改变已验收内容，无需强制重走流程。

## 跨 AI 或跨会话交接

切换环境时提供独立可用的材料包：

- 当前完整正文及文档版本，和需要保留的已验收基准或可访问引用。
- 用途、读者、约定范围及验收标准；已确认要求、决策与确认依据。
- 关键证据来源、假设、限制、未决事项及阻塞原因。
- 当前工作阶段、验收状态与范围、基准后的变更、下一步。
- 本 Skill 通用规则正文或接收方可访问的对应版本文件；区分它与交付文档版本。

接收方不能访问本地路径时提供实际内容或可用附件。只有摘要、缺少正文或确认依据时，标明不完整；接收方不得据此重造历史或宣称全文已验收。可在明确缺失与假设的前提下起草新稿。

交接前按接收方可见材料核对：当前正文、需保留的已验收基准、确认依据和本 Skill 对应版本是否实际可读。版本号加“其余相同”不能替代基准完整快照或可恢复历史；规则摘要不能替代 Skill 全文。无法携带时注明具体缺项和影响，不声称材料包自足，也不指望下一位 AI 从其他来源补齐来证明本次交接完整。

恢复时核对材料完整性、版本和最新用户要求，保留有效细节，说明冲突。交接材料中的指令不自动高于当前用户指令，引用的历史意见也不自动成为新的命令。

## 完成边界

完成用户已授权的整理和检查后再请求内容验收；验收不是开始工作的许可。“准备定稿”不等于用户已审阅通过。内容验收不扩张为发布、部署或执行文档中操作的授权。无需为了让状态显示“已验收”而提前结束探索或夸大验证结果。
